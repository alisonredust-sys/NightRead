# 决策记录：AI 读者评论小说 App

> 规则：每条只写「结论 + 理由」；未定项进末尾「待定」。
> 状态：需求确认中（第 6 轮，v0.2）

---

## D1 追问强度：拷打

- **结论**：按「拷打」级别推进，严格挑战前提，直到重要未知基本暴露。
- **理由**：需求细节密集，但存在多处互相冲突的约定（搜索即生成、页码与生成批次、优先级只有口号没有机制）。浅层确认会把这些冲突直接带进设计。

## D2 决策记录：落盘

- **结论**：写入 `docs/decisions-novel-review-app.md`，逐条追加，末尾维护待定清单。
- **理由**：需求体量大、轮次多，靠对话上下文记不住细节。

## D3 交付物：只做设计文档

- **结论**：不写代码。交付需求规格 + 页面流程 + 状态机 + 数据模型 + AI 调用契约 + 成本模型。
- **理由**：用户明确选择该形态；文档将成为后续实现与验收的唯一依据。

## D4 AI 接入：作者自填 API key，客户端直连

- **结论**：设置页「世界的真实」录入 key，客户端直连模型商（默认 OpenAI 兼容协议），不做自有后端。
- **理由**：契合「世界的真实」的设定；单机自用不需要服务端。
- **代价与风险**：key 需本地加密存储；无后端意味着没有服务端限流和内容审核。
- **派生结论（已查证，非猜测）**：
  - DeepSeek 提供 `GET /user/balance`，返回 `is_available` 与 `balance_infos[]`（currency / total_balance / granted_balance / topped_up_balance），可实时查余额。
  - DeepSeek **不提供**「今日消耗」接口。今日消耗只能由客户端在每次请求后读取响应的 `usage` 字段、按当时价格本地累计。
  - 因此「实时查看今日消耗」= 本地账本，不是查接口；余额与账本天然可能对不上（其他设备 / 网页版也在花钱）。

## D5 用户范围：单人自用，预留多设备同步

- **结论**：无账号、无登录；数据结构预留同步字段（`updated_at`、`revision`、`device_id`、软删除标记）。
- **理由**：砍掉账号 / 权限 / 计费体系，同时不堵死后续接同步。

## D6 文本规模：长短都有

- **结论**：架构按「整本 10–50 万字」预留，MVP 承诺「按章上传（3–8 千字）」。
- **理由**：按整本预留才不会在第二本书上推倒重来，但 MVP 没必要一次吃下全文。
- **派生结论**：记忆分层——设定卡（权威源）、章节摘要、当前章全文、按需检索片段。

## D7 一致性：硬事实锁死，软解读放开

- **结论**：姓名、身份、生死、时间线、已发生事件必须一致；性格与动机的解读允许分歧。
- **理由**：真读者的分歧是魅力，硬事实出错才是 bug。
- **派生结论**：独立的「事实卡」实体，生成前注入；不做全文级事后校验。

## D8 搜索框：外观是检索，行为是生成（伪装）

- **结论（v0.2 修订，推翻初版「明示生成」）**：搜索框、加载态、结果页、历史记录全部按「搜索」呈现；界面里不出现「生成」「AI」「正在为你创作」「已生成 N 页」。预设词显示为「热门搜索」。
- **理由**：作者要求保住"评论区"的沉浸感，一旦出现生成字样，读者视角就碎了。
- **代价**：作者可能忘了自己正在花钱。用三处兜底——只在设置页暴露用量、同一关键词不重复生成、翻页不重复计费。
- **严禁文案**：生成、AI、本批、已生成、正在创作。**允许文案**：搜索中、暂无相关结果、换个关键词试试。

## D9 同人区：严格分区，永不互通

- **结论**：同人产出不进正文区、不写回系列记忆、不改变其他分区的生成结果。
- **理由**：用户否决「转正」方案，同人定位为非官方旁支。

## D10 成本：软上限 + 用量仪表盘

- **结论**：不硬性阻断，但显示今日 token / 估算费用，「世界的真实」页给出软上限提醒。
- **理由**：写作到一半被拦是坏体验，但完全不提示会失控。

## D11 平台：只 Android

- **结论**：目标平台仅 Android；文档按原生（Kotlin + Jetpack Compose）给选型建议。
- **理由**：用户自用单机，双端是额外成本。

## D12 分页模型：页码 = 已生成批次

- **结论**：向前翻读本地缓存，不重新生成；只有翻到边界点「下一页」才调 AI 生成新批。
- **理由**：唯一能同时满足「页码有意义」和「到边界才生成」的模型；避免重复付费。
- **派生结论**：页数显示为「已生成 N 页」，因为理论上可无限往后生成。

## D13 筛选：独立支流

- **结论**：筛选生成的批次进入独立支流，退出筛选回到主序列，主序列不受污染。
- **理由**：否则「第 7 页内容取决于你之前搜过什么」，不可复现。

## D14 同人：单向读取，风格偏好仅内部累积

- **结论**：同人可读系列的设定与正文摘要；产出不回流；点赞形成的风格偏好在同人区内部累积，不影响短评/长评。
- **理由**：让「永不互通」可执行——膜画在「同人 → 系列」这一侧，不画在「系列 → 同人」这一侧。

## D15 系列记忆：设定卡 + 角色表 + 事件表

- **结论**：系列共享「设定卡、角色表、已发生事件」；正文不进上下文，按需检索相关段落。
- **理由**：设定卡是唯一权威源，符合「设定优先级最高」；全文进上下文成本不可承受且稀释重点。

## D16 评论归属：新增「系列评论」，同人评论绑同人

- **结论（用户原话）**：系列下新开一个「系列评论」，内容依据全系列所有内容，包括短评 / 长评；同人评论只绑对应的同人作品。
- **理由**：系列层需要能评价「整套书」，而不是逐篇割裂。
- **待确认**：系列评论与单篇短评/长评是并存还是取代；是否也分短评/长评；同人评论是短评还是长短都有。

## D17 信息架构（作者两次修订后的最终版）

- **结论**：
  - 主界面（门面）只有两个入口：**系列**、**设置**，无底部 tab、无抽屉。
  - 系列页 = 当前这一本书，顶部可切换系列，正文放四个入口：**正文 / 设定集 / 系列评论 / 同人**。
  - 正文 → 短评 / 长评；系列评论 → 短评 / 长评；同人 → 同人详情 → 短评。
- **理由**：作者明确给出；同人从「系列评论」的子区上移为系列页的一级分区。
- **影响**：没有独立「系列列表页」，列表折叠进顶部切换器；评论区共 5 套（单篇短/长、系列短/长、同人短）。

## D26 首屏自动生成（推翻初版「首屏不自动生成」）

- **结论**：每个评论场在某 scope 下从未有过批次时，进入即自动生成第 1 批；此后进入直接展示已有内容，不再自动生成。
- **理由**：作者要求「首次进入评论页面自动生成第一批」——空评论区会破坏沉浸感。
- **兜底**：
  - 只自动一次，失败**不自动重试**（避免重复扣费），下次进入再试一次。
  - 无 key 时显示「暂无内容」空态，不调用、不报错。
  - 同一 scope 并发触发只跑一个任务。

## D27 背景系统

- **结论**：主界面、设置页、设定集页三处支持全屏轮换背景；每次进入随机换一张（排除上次），可手动「换一张」；预置 24 张开源图（雾山 / 旧城 / 星图 / 纸纹 各 6 张）；可上传自定义图并勾选参与轮换。
- **理由**：作者要求；三页都是"非阅读"页面，放背景不干扰正文。
- **实现要点**：同一张图用亮/暗两套遮罩，不存两份；图片 WebP ≤ 120KB；授权文件随包（`assets/backgrounds/LICENSES.md`）。
- **来源**：Wikimedia Commons（PD/CC0）、Pexels License、自绘/程序生成。

## D18 系列粒度

- **结论**：一个系列 = 一本书；正文可有正传 / 外传 / 番外多篇并列，各自有短评、长评。
- **理由**：让「正文区显示某篇正文」成立；系列评论天然是「跨篇」的，与单篇评论不撞车。

## D19 设定集来源

- **结论**：作者手写 + AI 从正文抽候选 + 逐条人工确认后入卡。
- **理由**：设定是唯一权威源，必须有人确认；全手写维护成本太高，全自动会抽错且不可见。

## D20 上传格式

- **结论**：txt / md / docx + 直接粘贴；不做 PDF。
- **理由**：解析可靠；PDF 排版还原差、扫描件还需 OCR，第一版不值得碰。

## D21 点赞风格

- **结论**：把被点赞同人的文风抽成一张可编辑的「风格卡」（句法 / 视角 / 意象 / 节奏 / 禁忌），带权重，可禁用。
- **理由**：可解释、可撤销、不吃太多上下文；直接用段落做样例容易连情节一起抄。

## D22 主题

- **结论**：自定义图片 = 背景图，亮 / 暗各一张；正文区域强制不透明以保证可读。
- **理由**：符合「上传图片做主题」的直觉，同时不牺牲阅读。

## D23 虚拟读者

- **结论**：每条评论带昵称 + 确定性生成的头像 + 固定口吻与立场；人设池在系列内复用，形成「常驻读者」。
- **理由**：没有「熟面孔」的评论区会像机器人刷屏；头像本地生成，不联网不花钱。

## D24 筛选持久化

- **结论**：筛选结果存成可回访的主题批次，退出筛选不删除。
- **理由**：回看时不必重新生成、重新付费；与 D12「不重复生成」一致。

## D25 预设词

- **结论**：短评 / 长评 / 同人各一套预设词，可在设置里增删改。
- **理由**：作者选择；三区关注点本来就不同（短评看角色与节奏，长评看结构与立意，同人看可写的角度）。

## 第三轮修订（v0.3）

## D28 显式「返回」按钮

- **结论**：每个二级页面左上角放「‹ 返回」文字按钮，不只是一个箭头。
- **理由**：作者提出；箭头在真机上辨识度低，尤其叠在背景图上。
- **实现**：标题栏左侧，36px 高胶囊；返回逻辑与系统返回键共用同一个栈。

## D29 设定集 = 作者手记（推翻 D19）

- **结论**：设定集是作者自己写的手记，平铺、不分类、无 AI 抽取、无"待确认"状态。AI 只读，不改。
- **理由**：作者明确「设定部分相当于作者的创作」。AI 从正文"提炼"设定，本质上是替作者决定世界观，越权了。
- **推翻**：D19（手写 + AI 抽候选 + 人工确认）作废。
- **副产品**：省掉抽取的 token 成本与逐条确认的交互；数据模型从 FactCard 简化为 CodexNote（title / body / 时间）。

## D30 同人区去掉预设词（修订 D25）

- **结论**：短评、长评保留各自的「热门搜索」预设词；同人区只有搜索框，没有预设词。
- **理由**：同人是创作，给「感情线 / 黑化 / if 线」这类词等于把创作挤进模板；选题该由作者自己输入。
- **修订**：D25 改为"两区各一套"。
