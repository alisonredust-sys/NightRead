# 饮食体重记录 App — 设计决策记录

- 状态：**设计定稿（待用户确认规格书后开发）**
- 访谈强度：5（拷打，已完成 8 轮）
- 最近更新：2026-11-15

---

## 一、原始需求（用户原话要点）

- **R1** 每日记录体重、体脂率；输入方式为数字键盘，或标记「未记录」。
- **R2** 每日记录六顿饮食：早餐 / 上午 / 午餐 / 下午 / 晚餐 / 夜宵；文本自由输入。
- **R3** 记录数据可导出为 Excel 表格；起止日期可自由选择。
- **R4** 内置简易计算器：计算任意时间段的平均体重；绘制任意时间段的体重变化情况。

> 需求以「每日」为单位表述，但「每日一条」是否成立尚未确认（见 Q4）。

---

## 二、已确定的决策

### D1｜访谈强度 = 5（拷打）

- **结论**：以严格挑战前提、主动寻找风险与边界情况的方式进行需求确认。
- **理由**：用户要求确认「所有细节」，并接受深度追问；自用工具型 App 的失败点通常不在功能缺失，而在未验证的默认假设。
- **影响**：每轮问题数量不必多，但每个问题都要指向会改变方案的分歧点。

### D2｜保留决策记录（本文件）

- **结论**：每确定一条追加「结论 + 理由」，并维护独立的待定问题清单。
- **理由**：细节轮次多，几轮后难以回溯「当初为什么这么定」；后续加功能时需要对照。

### D3｜使用范围 = 仅本人自用，不上架

- **结论**：不做账号体系、不做云同步、不做多用户数据隔离、不处理商店合规与隐私政策。
- **理由**：自用场景下上述三项是成本最高的部分，砍掉后可以把精力放在录入体验与统计正确性上。
- **影响**：
  - 分发方式为自行安装（APK / 调试包），无需签名发布流程。
  - 数据仅存在本机；**换手机、重装、误删即数据丢失**，备份策略上升为必须回答的问题（见风险 R-1）。
  - 代码层面仍不写死「单用户」假设（不加 user_id 表，但数据访问层保持单入口），避免日后想给家人用时推翻重来。

---

### D4｜数据粒度：一天一条记录

- **结论**：每个自然日最多一条记录，包含体重、体脂率、六顿饭文本。
- **理由**：用户选择 A（一天一条），每日单值即可支撑趋势图与平均值，交互最省。
- **代价（已接受）**：不记录称重时间，一天内的体重波动不可见；趋势反映的是「称重时刻的读数」而非「真实体重」。
- **同一天重复提交**：以最后一次为准，覆盖旧值。

### D5｜「未记录」的表示：字段留空（NULL）

- **结论**：体重、体脂率各自独立可空；不存 0、不存「未记录」字样、不设哨兵值。
- **理由**：0 会系统性拉低均值；文字会破坏 Excel 直接求和/求平均的能力；NULL 是唯一同时满足「导出为空单元格」与「统计可跳过」的表示。
- **遗留**：平均值分母（有效天数 vs 区间日历天数）尚未确定，留到统计轮。

### D6｜一天的边界：自然日 + 手动改归属日期

- **结论**：以 00:00 切分自然日；录入时允许手动把记录改挂到另一个日期（覆盖「凌晨补记昨晚夜宵」的场景）。
- **理由**：导出结果可解释；避免「作息日（凌晨 4 点切）」这种隐含规则造成的口径混乱。

### D7｜六顿饭：固定六个槽位，允许留空

- **结论**：六个槽位固定存在，任一槽位可为空（当天没有上午加餐是常态）。
- **理由**：用户明确说明上午/下午/夜宵并非每天都有。
- **待确认**：空槽是否还需区分「没吃」与「忘了记」（Q8）。

### D8｜空槽不区分「未进食」与「未记录」

- **结论**：六个槽位留空即视为「无内容」，不额外标记「没吃」。
- **理由**：用户选择最简方案，减少每次录入的点击与判断。
- **代价（已接受）**：「漏记」与「真的没吃」在数据层不可区分，将来无法统计「这个月有几天跳过了早餐」。若日后需要，只能新增字段，历史数据无法回填。

### D9｜未来日期：禁止（补记范围待澄清）

- **结论**：不允许录入未来日期的体重/体脂/饮食。
- **理由**：未来记录会污染连续记录天数、趋势图右端与区间平均值。
- **待澄清**：Q9 的回答「不能」同时可能指向「不能补记过去」，二者结论相反，需 Q12 确认。

### D10｜录入界面：单页表单，一天一屏

- **结论**：体重、体脂、六顿饭共七项在同一屏内完成录入。
- **理由**：用户选择 A；需要一屏看全当天，便于核对与修改。
- **待定**：保存方式（自动保存 vs 显式「保存」按钮）。

### D11｜体重单位：显示用「斤」，保留 1 位小数

- **结论**：界面显示与默认导出以「斤」计，保留 1 位小数（如 128.5 斤）。
- **理由**：用户日常口径为斤。
- **衍生约束**：存储必须以 kg、**2 位小数**保存（0.1 斤 = 0.05 kg），否则每次换算都会累积舍入误差。
- **待确认**：体脂率是否同样 1 位小数；导出是否同时给出「斤」与「公斤」两列。

### D12｜日期：可补记任意过去日期，禁止未来日期

- **结论**：录入页允许选择任意过去日期补记；不允许未来日期。
- **理由**：漏记一天不应导致永久缺口；补的仍是真实数据，不污染统计。未来数据会污染趋势右端与平均值区间。
- **衍生**：录入页需要一个日期选择器（默认今天），且需要「回到今天」的快捷方式。

### D13｜导出范围：区间内每一天一行

- **结论**：导出的行数 = 起止日期包含的天数；无记录的天保留日期列、其余列留空。
- **理由**：用户选择 A；「哪天漏记」本身是有效信息，行数=天数也便于在 Excel 里计算记录率与连续天数。

### D14｜导出格式：xlsx 单表，日期为真日期

- **结论**：导出 `.xlsx`，单 sheet，日期列写入真日期类型（显示格式 yyyy-mm-dd）。
- **理由**：用户选择 xlsx；真日期才能在 Excel 里排序、透视、按周/月聚合。
- **待确认**：日期类型一项用户仅回答了格式，按建议采纳真日期。

### D15｜导出落地：直接写入「下载」目录

- **结论**：导出文件写入系统「下载」目录，完成后提示完整路径。
- **理由**：用户选择 B；少一次选择对话框。
- **衍生约束**：Android 10+ 需通过 MediaStore 写入 Downloads（无需存储权限）；Android 9 及以下需申请写外部存储权限。
- **待确认**：是否在导出成功后附带一个「分享」按钮（发微信/邮件），否则文件出手机需要另找入口。

### D16｜统计输出：平均值 + 样本量 + 极值 + 变化量

- **结论**：区间统计同时给出：平均体重、有效天数 n 与区间总天数、最高、最低、首尾差（末条 − 首条）、变化率。
- **理由**：用户选择 C。单个平均数无法判断方向、波动幅度与可信度；「n=16/30」是解释这个平均值的必要前提。
- **口径**：平均值的分母 = **有记录的体重天数**（缺失日不参与）；体重与体脂分别统计，不要求同一天两者都有。

### D17｜图表：缺失日跨点直连

- **结论**：缺失日不补点、不阶跃，曲线由前后两个有效记录点直接连线。
- **理由**：用户选择 B，偏好视觉连续。
- **代价（已记录）**：连线斜率代表一段从未测量的区间，读者容易误读为「那段时间体重是平滑变化的」。
- **待确认**：时间轴刻度（日历等距 / 记录点等距），以及是否把跨缺失段画成虚线以标记「插值」。

### D18｜体脂率不上图

- **结论**：趋势图只画体重；体脂率仅出现在录入表单与导出表格中。
- **理由**：用户选择 A；避免双 Y 轴的刻度误读与体脂日间噪声干扰。

### D19｜不设目标体重

- **结论**：不做目标体重线、不做进度百分比、不做预计达成日期。
- **理由**：用户选择 A；只关注实际变化。

### D20｜图表：日历等距 + 虚线跨缺失段

- **结论**：横轴按日历日等距（每天同宽），缺失日不占数据点；跨缺失段的连线用虚线，其余为实线。
- **理由**：用户答「①②」，按「时间轴①（日历等距）+ 缺失段②（虚线）」解读，与「跨点直连」的选择相容。
- **效果**：既保留视觉连续，又能在图上区分「测过」与「插值」。
- **若理解有误**：若本意是实线，改为全程实线即可，其余不变。

### D21｜历史浏览：今日表单 + 日期切换

- **结论**：只有一套表单界面；顶部显示当前日期，左右箭头翻前后一天，点日期弹日历跳转。
- **理由**：用户选择 A；避免维护日历页与列表页两套状态。
- **衍生**：需要「回到今天」的显式入口，否则翻到三个月前后容易迷路。

### D22｜删除：立即生效，仅二次确认

- **结论**：删除记录不设回收站、不与撤销；只弹一次确认。
- **理由**：用户选择 A。
- **风险（已记录）**：一次误触即可永久删除一条记录，且本机无任何备份（D3）。此决定与 D3 共同构成数据安全的单点风险，需在第七轮与备份方案一起复核。

### D23｜不做每日提醒

- **结论**：不申请通知权限，不做提醒。
- **理由**：用户选择 A；减少权限与后台任务，也不引入「被系统杀掉后台」的故障面。

### D24｜备份：不做

- **结论**：不实现备份/恢复，不做云同步；Excel 导出是唯一把数据带出手机的形式。
- **理由**：用户在 Q24 选择 C（历史数据非关键资产）、Q26 选择 C（不做备份）。
- **代价（用户已确认接受）**：换手机、重装、误删 = 历史数据全部清零，且无法挽回。
- **影响面**：数据层可以做得更简单（无版本迁移需求、无导入校验）；但代码中**不得**假设数据可恢复。

### D25｜交付方式：本机装环境，产出可安装 APK

- **结论**：在本机安装 JDK 17/21 与 Android SDK（cmdline-tools），用 Gradle wrapper 构建 debug APK 交付，用户自行安装。
- **环境验证（2026-11-15）**：`dl.google.com` 200 / 0.85s，Maven Central 200 / 2.2s，`services.gradle.org` 200 但首包 18s（偏慢，必要时换国内镜像）；L 盘 107 GB 可用。
- **风险**：Gradle/AGP 依赖首次下载慢；JDK 25 对 AGP 偏新，实测不通过时降级安装 JDK 17。

### D26｜目标平台：minSdk 26，target/compile 36

- **结论**：最低 Android 8.0（API 26），targetSdk 与 compileSdk 均为 36（Android 16）。
- **理由**：用户手机为 Android 16；minSdk 26 可直接使用 MediaStore 写「下载」目录，省掉旧版权限分支。

### D27｜技术栈：Kotlin + Jetpack Compose + Room（由我代为决定）

- **结论**：单 Activity + Compose；Room/SQLite 存储；图表用 Canvas 自绘；xlsx 用 `java.util.zip` 手写 OOXML，不使用 Apache POI。
- **理由**：用户明确不熟悉技术、授权我决定。Android-only（D3），且需要自绘数字键盘与折线图，原生方案依赖最少、体积最小；POI 带来约 10 MB 体积与 Android 上的 API 兼容问题，而这里只需写一张表。
- **影响**：APK 目标 < 15 MB；无第三方 SDK、无网络权限。

### D28｜导航：两个 tab + 导出二级页

- **结论**：底部两个 tab ——「记录」「统计」；导出入口在记录页右上角，进入独立页面。
- **理由**：用户选择 B；导出是低频操作，不值得占用常驻导航位。

### D29｜保存方式：全自动，无按钮、无提示

- **结论**：字段失焦 / 键盘收起 / 页面切换时静默写库，界面不显示「已保存」。
- **理由**：用户选择 A。
- **实现约束**：写入异常时必须回退为可见提示——否则等于静默丢数据。这条不改变交互，只保证失败不被吞掉。

### D30｜导出表头：10 列，无星期、无备注

- **结论**：`日期 | 体重(斤) | 体重(kg) | 体脂率(%) | 早餐 | 上午 | 午餐 | 下午 | 晚餐 | 夜宵`；体脂 1 位小数；单元格自动换行。
- **理由**：用户确认。

## 五、已识别风险（定稿）

### R-1｜换机即丢数据 —— 已决定接受，不做补救

用户两次选择「最简方案」（Q24=C、Q26=C），因此**不做备份/恢复**。Excel 导出是唯一的外带形式，且是单向快照：无法回灌、多次导出散落成多个文件。
**状态**：已接受（D24）。若日后反悔，最低成本补救是设置页一个「导出 JSON / 从 JSON 恢复」，其余架构无需改动。

### R-2｜「平均体重」的分母陷阱

若把「未记录」当 0 或当缺失日参与计算，平均值会系统性偏低或偏高。平均值必须同时显示有效样本数（n 天 / 区间总天数），否则数字本身不可解释。

### R-3｜称重时间漂移污染趋势

人体一天内体重波动可达 1–2 kg。若称重时间不固定，趋势图反映的是「称重时刻」而非「体重变化」。这是 Q4 的真正动因。
